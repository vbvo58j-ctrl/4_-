# المرحلة 16 — استقبال المحادثات الفردية على مستوى التطبيق

## ما تم دمجه
- نقل استقبال حزم Ratchet الفردية من الاعتماد على شاشة المحادثة وحدها إلى `MeshRuntimeService` الذي يبدأ مع التطبيق ويستمع إلى Bluetooth وWi-Fi Aware وLAN.
- فك الحزمة والتحقق من هوية المرسل وتوقيعه ووجهتها ومعرّف المحادثة قبل حفظ الرسالة.
- حفظ الرسائل الفردية الواردة في `MessageStore` حتى عند الانتقال إلى تبويب آخر أو إغلاق شاشة المحادثة.
- إصدار `delivery_ack` مشفر عبر جلسة Ratchet من runtime؛ إذا كان المرسل هو القفزة السابقة يرد عبر نفس النقل، وإلا يضع الإيصال في طابور Mesh.
- فك إيصالات `delivery_ack` و`read_ack` على مستوى التطبيق وتحديث حالة الرسالة دون الحاجة إلى فتح ChatScreen.
- إزالة ازدواج المعالجة عند وصول الحزمة نفسها عبر أكثر من ناقل باستخدام قفل مؤقت لكل packet ID وعلامة persisted بعد الحفظ.
- إضافة بث تحديثات MessageStore لكي تتحدث شاشة المحادثة المفتوحة عندما يحفظ runtime رسالة أو يحدّث إيصالاً.
- تسلسل عمليات الكتابة إلى مخزن الرسائل لمنع فقدان التحديثات عند وصول رسالة وإيصال بالتزامن.
- الإبقاء على إيصال القراءة مرتبطاً بفتح المحادثة فعلياً؛ runtime يصدر إيصال التسليم فقط، والشاشة تصدر إيصال القراءة عند عرض الرسالة.

## الحدود والفحوص
- لم يتم بناء APK أو تشغيل `flutter analyze` أو اختبارات Dart لأن أدوات Flutter/Dart/Gradle غير متاحة في بيئة التنفيذ.
- لم يتم اختبار النقل بين هاتفين فعليين. يلزم اختبار: وصول الرسالة والشاشة مغلقة، وصولها عبر Bluetooth وWi-Fi معاً، إيصال التسليم عبر وسيط Mesh، فتح المحادثة لإصدار read_ack، وإعادة تشغيل التطبيق أثناء وجود رسائل واردة.
- معالجة مرفقات الرسائل الفردية الكبيرة لا تزال تعتمد على بروتوكول file-chunk الموجود؛ لا يعالج هذا التعديل بدائل أو تغييرات في تشفير المجموعات.
