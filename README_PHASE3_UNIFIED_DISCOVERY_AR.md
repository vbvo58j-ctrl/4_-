# المرحلة التالية: سجل موحد وآمن لاكتشاف مستخدمي بلوساب

## ما تم تغييره في هذه المرحلة
- إضافة `NearbyPeerDirectory` كسجل مركزي واحد للهويات القريبة.
- يستقبل السجل أحداث Bluetooth بعد `blousabVerified` فقط، أي بعد نجاح المصافحة المتبادلة الموقعة وتحدي nonce.
- دمج اتصالات Bluetooth المتعددة تحت `userId` واحد، ومنع تكرار نفس الحساب في قائمة النتائج.
- استقبال إشارات Wi-Fi Aware وتسجيلها كمرشحين داخليين، مع عدّاد مستقل لها.
- لا تتحول إشارة Wi-Fi Aware المعلنة إلى حساب ظاهر أو موثوق بمجرد احتوائها على `userId` واسم؛ بيانات الإعلان الحالية ليست موقعة ولا تتضمن مصافحة nonce.
- تحديث نافذة البحث لتقرأ من السجل الموحد، ولا تعرض أسماء أجهزة Android أو نتائج Wi-Fi غير الموثقة كحسابات.
- لا يبدأ الاتصال أو المحادثة بمجرد الاكتشاف. يختار المستخدم حساباً موثقاً صراحةً.
- عند وجود مرشح Wi-Fi بنفس المعرّف، تعرض الواجهة أنه رُصدت إشارة Wi-Fi لكنها تنتظر توثيقاً مستقلاً؛ ولا تستخدم قناة Wi-Fi قبل هذا التوثيق.

## لماذا لم ندمج Wi-Fi Aware كهوية موثقة بعد؟
إعلان NAN الحالي في `MainActivity.kt` يبث `BLOUSAB|userId|userName` نصاً واضحاً. يمكن لأي تطبيق قريب تقليد هذا الإعلان. دمج هذه الإشارة مع هوية Bluetooth اعتماداً على تطابق `userId` فقط قد يسمح بانتحال مستخدم أو توجيه البيانات إلى طرف غير صحيح. لذلك أبقيناها مرشحاً غير موثوق بدلاً من الادعاء أن المصافحة اكتملت.

## العمل المتبقي في المرحلة التالية
- إضافة تبادل هوية Ed25519 موقعة عبر رسائل Wi-Fi Aware.
- إضافة تحدي nonce متبادل مستقل لكل جلسة Wi-Fi Aware والتحقق من التوقيع قبل إصدار حدث `wifiIdentityVerified`.
- ربط الهوية الموثقة نفسها بين Bluetooth وWi-Fi عبر المفتاح العام وبصمة الهوية، لا عبر `userId` وحده.
- بعد ذلك فقط يسمح السجل الموحد باستخدام القناتين، ويعرض رمز النقل الصحيح، مع إزالة المسار عند `userLost` أو `dataDisconnected`.

## التحقق
- راجعت تدفق الاكتشاف في Dart وKotlin يدوياً.
- لم يتم تشغيل `flutter analyze` أو اختبارات Flutter أو بناء APK في هذه البيئة لعدم توفر Flutter/Dart وAndroid SDK.
- يلزم البناء واختبار هاتفين فعلياً، ويفضل أن يدعم الهاتفان Wi-Fi Aware، قبل اعتبار اكتشاف Wi-Fi موثقاً ومكتملًا.
