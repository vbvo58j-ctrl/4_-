# المرحلة 15 — تشفير إيصالات التسليم والقراءة

## ما تغير
- أصبحت إيصالات `delivery_ack` و`read_ack` تُنشأ كحمولة داخلية ثم تُشفّر عبر `PairwiseChainRatchetService` باستخدام جلسة المحادثة الفردية نفسها.
- لا تظهر حقول `ackFor` أو نوع الإيصال أو اسم المرسل في الحزمة الخارجية؛ تبقى فقط بيانات التوجيه اللازمة للـ Mesh وهوية الطرفين ومعرّف الحزمة.
- الإيصالات تمر عبر مسارات الإرسال نفسها (Bluetooth وLAN/Wi-Fi Aware) وتبقى قابلة للتمرير كـ ciphertext عبر الوسطاء.
- عند وصول الحزمة إلى شاشة المحادثة، يعالجها مسار `blousab_pair_chain_message` ويفكها ويتحقق من تطابق المرسل والمستلم ومعرّف الرسالة والمحادثة قبل تحديث حالة الرسالة.
- لا يتم إرسال إيصال غير مشفر كحل احتياطي عند غياب جلسة Ratchet؛ يسجل التطبيق الخطأ بدلاً من كشف حالة التسليم/القراءة.

## ملفات التغيير

## حدود معروفة
- معالجة الإيصال النهائي وتحديث حالة الرسالة ما زالا مرتبطين بمسار استقبال المحادثة؛ إذا كان التطبيق لا يشغّل شاشة المحادثة عند وصول الإيصال، قد يتأخر تحديث الحالة حتى إعادة فتحها. يجب نقل فك الإيصالات إلى موزّع app-scoped واحد قبل اعتبار الإيصالات مستقلة تماماً عن الواجهة.
- الوسطاء لا يستطيعون قراءة `ackFor` أو تمييز إيصال القراءة عن التسليم، لكن بيانات التوجيه الخارجية (معرّف الحزمة، الطرفان، المحادثة، التوقيت) تبقى ظاهرة لتشغيل Mesh.
- هذه الخطوة لا تضيف تشفيراً مستقلاً لإشارات الاتصال/المصافحة؛ المصافحة موقعة وموجهة وليست محتوى محادثة.
- لم يتم بناء APK أو تشغيل Flutter analyze/tests أو اختبار هاتفين لعدم توفر Flutter/Dart/Gradle في بيئة التنفيذ.
