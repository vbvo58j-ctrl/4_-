# المرحلة 12 — أساس Ratchet للمحادثات الفردية (تجريبي وغير موصول بالنقل)

أضيف `PairwiseChainRatchetService` كبداية بروتوكول قابلة للمراجعة:

- مصافحة offer/answer بمفتاحي X25519 مؤقتين مستقلين، مع توقيع Ed25519 والتحقق من مفتاح الطرف المثبت سابقاً عبر QR.
- اشتقاق جذر جلسة وchain منفصل للإرسال والاستقبال باتجاهين مختلفين.
- اشتقاق مفتاح مستقل لكل رسالة، وتحديث السلسلة أحادي الاتجاه بعد كل رسالة.
- عدادات، ونافذة مفاتيح للرسائل المتأخرة بحد 128، ورفض الرسائل المكررة/القديمة خارج النافذة.
- تخزين حالة الجلسة والمفاتيح الحالية في FlutterSecureStorage.

## حدود أمنية مهمة

هذه **ليست Double Ratchet مكتملة**: لا يوجد DH-ratchet دوري، ولا prekeys أحادية الاستخدام/خادم prekey، ولا post-compromise security. كما أن هذه المرحلة لا تدّعي forward secrecy نهائية قبل مراجعة دورة حياة المفاتيح واختبارات اختراق/تزامن. الخدمة معزولة وغير موصولة بمسارات الرسائل الحالية عمداً؛ توصيلها قبل إضافة تفاوض session control وإعادة ترتيب/إقرار آمن قد يقطع المحادثات القائمة أو يسبب فقد رسائل.

مفاتيح المجموعة الحالية في المرحلة 11 ما زالت group AES-GCM epochs وليست sender-key ratchets؛ لم يتم تغييرها في هذه المرحلة. كما أن receipts/control packets لم تتحول بعد إلى Ratchet.

## المطلوب قبل التفعيل

1. مراجعة API ونسخة `cryptography` على Flutter/Android وبناء المشروع فعلياً.
2. اختبارات تبادل offer/answer بين جهازين، الرسائل بالترتيب وخارج الترتيب، التكرار، القفزات الكبيرة، إعادة التشغيل، انقطاع/تزامن التخزين، وتغيير الهوية.
3. إضافة DH-ratchet دوري وتدوير/حذف المفاتيح المؤقتة، ثم sender-key ratchet للمجموعات.
4. بعد نجاح الاختبارات فقط: ترحيل الرسائل الفردية والملفات والإيصالات والتحكم تدريجياً مع توافق/ترحيل آمن للرسائل القديمة.
