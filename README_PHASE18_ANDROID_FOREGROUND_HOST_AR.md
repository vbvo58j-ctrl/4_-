# المرحلة 18 — تأسيس خدمة Android Foreground Runtime

## ما أضيف
- خدمة Android أصلية `BlousabBackgroundService` بنوع `connectedDevice`.
- إشعار دائم واضح عند تشغيل خدمة الخلفية.
- صلاحيات Android المطلوبة لخدمة Foreground على الإصدارات الحديثة.
- قناة MethodChannel لتشغيل الخدمة وإيقافها والاستعلام عن دعمها.
- تشغيل الخدمة بعد اكتمال تدفق الإعداد الأولي وبدء MeshRuntimeService.
- `START_STICKY` لإعادة إنشاء مضيف الخدمة إذا أعاد Android إنشاء العملية.

## حدّ التنفيذ المهم
هذه المرحلة **لا تنقل نقل Bluetooth أو Wi-Fi Aware أو LAN إلى الخدمة بعد**. هذه المقابس ومستمعات الأحداث ما زالت مملوكة لـ `MainActivity`، و`onDestroy()` فيها يوقف النقل. كما أن خدمة Foreground لا تعيد بناء حالة Dart أو جلسات Ratchet أو مفاتيح التشفير تلقائياً. لذلك لا يجوز اعتبار الإرسال بعد إغلاق التطبيق أو بعد إعادة تشغيل الهاتف مكتملاً في هذه المرحلة.

الخدمة الحالية هي مضيف Android وإشعار تشغيل فقط، وليست ادعاءً بأن النقل الشبكي يعمل في الخلفية. لم نضف Boot Receiver لأن تشغيل خدمة متصلة بالأجهزة بعد الإقلاع يحتاج تحققاً من قيود Android وإعادة تهيئة الأذونات والهوية والجلسات أولاً.

## الخطوة المطلوبة لإكمال الخلفية الحقيقية
1. نقل Bluetooth RFCOMM وWi-Fi Aware callbacks والسوكيتات من `MainActivity` إلى مكوّن Android مستقل طويل العمر.
2. إبقاء Flutter/Dart runtime أو إنشاء طبقة native transport مستقلة تتعامل مع صندوق الرسائل المشفر دون فتح شاشة.
3. استعادة هوية الجهاز وحالة Outbox بأمان دون تخزين مفاتيح Ratchet في ملفات مكشوفة.
4. إعادة اكتشاف الأقران ومصافحة الهوية قبل إرسال أي حزمة بعد استعادة الخدمة.
5. إضافة WorkManager/Boot recovery وفق قيود Android وإذن المستخدم، واختبار Doze وإيقاف التطبيق وإعادة تشغيل الهاتف.

## التحقق
- فحص Manifest ووجود service declaration والصلاحيات.
- فحص نقاط MethodChannel وربط التشغيل عند بدء Mesh.
- لم يتم تنفيذ Gradle build أو Flutter analyze أو اختبار جهاز فعلي؛ يلزم ذلك قبل اعتماد المرحلة إنتاجياً.
