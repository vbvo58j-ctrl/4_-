# المرحلة الرابعة — ربط سجل الاكتشاف بمفتاح Ed25519

## ما تم تعديله
- أضيف `publicKey` إلى نموذج أحداث Bluetooth في Flutter.
- أصبحت أحداث `blousabVerified` الثلاثة الصادرة بعد مصافحة Bluetooth تحمل المفتاح العام الذي جرى التحقق منه فعلياً في Android.
- يحتفظ `NearbyPeerDirectory` بالمفتاح العام ضمن سجل المستخدم الموثق.
- يرفض السجل دمج حدث يحمل `userId` موجوداً مسبقاً إذا كان مفتاح Ed25519 مختلفاً. هذا يمنع دمج هويتين مختلفتين لمجرد ادعائهما نفس معرّف المستخدم.
- بقيت إعلانات Wi-Fi Aware الحالية مرشحات غير موثوقة؛ لا تنشئ مستخدماً ظاهراً ولا تفتح مسار نقل.

## ما لم يكتمل بعد
هذه ليست مصافحة Wi-Fi Aware بعد. الإعلان الحالي `BLOUSAB|...` ما زال نصاً قابلاً للتقليد، ولذلك لا يجوز اعتباره إثبات هوية. ما زال المطلوب تنفيذ تبادل رسائل عبر `DiscoverySession.sendMessage` يتضمن هوية موقعة، nonce جديداً من الطرفين، وتوقيع transcript موحداً من مفتاح Ed25519 نفسه، ثم مقارنة المفتاح مع الهوية المرتبطة عبر Bluetooth قبل دمج المسارين. يجب ألا يصدر حدث `wifiIdentityVerified` قبل نجاح كل هذه الخطوات.

## التحقق
- يجب أن يحمل كل حدث `blousabVerified` مفتاحاً عاماً غير فارغ؛ وإلا يرفضه سجل الاكتشاف.
- يجب رفض مفتاح مختلف لنفس `userId`.
- لا يتغير سلوك اختيار المستخدم: الاكتشاف لا يبدأ اتصالاً تلقائياً.
- لم يتوفر Flutter/Dart أو Android SDK في بيئة العمل؛ لذلك لم ينفذ `flutter analyze` أو بناء APK أو اختبار هاتفين. يجب إجراء هذه الاختبارات على بيئة Android فعلية قبل اعتماد المرحلة إنتاجياً.
