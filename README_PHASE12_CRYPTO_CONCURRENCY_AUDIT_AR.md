# المرحلة 12 — تدقيق التزامن ومنع إعادة التشغيل في التشفير

## ما تم تنفيذه

1. **تسلسل تحديث قائمة replay للرسائل الفردية:** أصبحت قراءة/تعديل/حفظ قائمة `blousab_e2e_seen_v1` عملية متسلسلة داخل خدمة الهوية، حتى لا تقبل عمليتان متزامنتان الظرف نفسه بسبب سباق بين listeners.
2. **قفل حالة تشفير المجموعات:** تمت إضافة طابور عمليات متسلسل داخل `GroupE2eCryptoService`، ويشمل:
   - تدوير epoch ومفتاح المجموعة.
   - قبول حزمة مفتاح جديدة وتحديث epoch المحلي.
   - تشفير رسالة/ملف جماعي أثناء قراءة المفتاح الحالي.
   - التحقق من الرسالة الجماعية وفكها وتسجيل replay قبل السماح لعملية أخرى بفحص الحالة نفسها.
3. **معالجة مستمعين متعددين:** يبقى cache فك الرسائل الجماعية داخل العملية حتى يستطيع أكثر من listener داخلي استهلاك الرسالة التي تم فكها بالفعل، بينما ترفض إعادة التشغيل بعد إعادة تشغيل التطبيق.
4. **الحفاظ على النقل الحالي:** لم تتغير صيغ الحزم أو أسماء القنوات أو آلية Mesh؛ الهدف هو تقليل سباقات الحالة دون كسر التوافق مع المرحلة 11.

## ما كشفه التدقيق الأمني

- التشفير الفردي الحالي يعتمد X25519 ثابتاً للطرفين مع HKDF وAES-GCM وتوقيع Ed25519. هذا يوفر سرية/سلامة محتوى عند صحة مفاتيح الثقة، لكنه **لا يوفر Forward Secrecy**؛ إذ إن تسرب مفتاح X25519 الثابت قد يتيح اشتقاق مفاتيح الرسائل القديمة إذا توفرت التسجيلات.
- مفاتيح المجموعة الحالية AES-GCM ثابتة داخل كل epoch. تدويرها عند تغيّر العضوية يحد من وصول العضو المستبعد إلى epoch الجديد، لكنه **ليس Double Ratchet ولا Sender-Key Ratchet** ولا يحقق Forward Secrecy لكل رسالة.
- قوائم replay في SharedPreferences ليست قاعدة بيانات معاملاتية بين عمليات Android المنفصلة. التسلسل المضاف يحمي listeners داخل نسخة الخدمة الواحدة في isolate واحد، ولا يدعي الحماية من عدة عمليات/نسخ تطبيق متزامنة.
- تخزين مفاتيح epochs السابقة يظل سياسة توافق محدودة، وليس ضماناً لمسح كل نسخ المفاتيح من الذاكرة أو النسخ الاحتياطية أو سجلات النظام.
- رسائل الإيصالات وبعض رسائل التحكم ليست جميعها مغطاة بتشفير E2E شامل حتى هذه المرحلة.

## ما لم يتم تنفيذه بعد

- لم تتم إضافة Double Ratchet للمحادثات الفردية.
- لم تتم إضافة X3DH/Prekeys أو مصافحة ephemeral متبادلة لتأسيس جلسة ratchet.
- لم تتم إضافة Sender Keys ذات chain ratchet للمجموعات.
- لم تتم إضافة post-compromise security أو ادعاء تحقق Forward Secrecy.
- لم يتم تحويل receipts/control إلى envelopes E2E موحدة.

هذه النقاط تحتاج بروتوكول جلسة واضحاً مع رسائل تأسيس/تجديد، counters، skipped message keys محدودة، معالجة الرسائل خارج الترتيب، واختبارات تبادل ثنائية الاتجاه قبل ربطها بمسار النقل الحالي. لا يصح إعلان Double Ratchet لمجرد إضافة مفاتيح مؤقتة أو تغيير AES key دورياً.

## الفحوص المتاحة في بيئة التعديل

- فحص نصي لوجود طوابير التسلسل في المسارات الحساسة.
- فحص توازن الأقواس للمصادر المعدلة.
- فحص سلامة ZIP بعد إنشائه.

لم تتوفر أدوات Flutter أو Dart أو Gradle في بيئة التنفيذ؛ لذلك لم يتم تشغيل `flutter analyze` أو اختبارات Dart أو بناء APK أو اختبار هاتفين فعلياً.
