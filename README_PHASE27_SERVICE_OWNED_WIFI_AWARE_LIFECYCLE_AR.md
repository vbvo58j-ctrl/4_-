# المرحلة 27 — ملكية دورة حياة Wi-Fi Aware داخل خدمة Android

## الهدف
تقليل اعتماد اكتشاف Wi-Fi Aware على عمر `MainActivity` بنقل إنشاء جلسة NAN وإدارة publish/subscribe وإغلاق الموارد إلى `BlousabBackgroundService`، مع الحفاظ على بروتوكول الهوية والمصافحة الحالي دون تغييره.

## التغييرات
- أضافت `BlousabBackgroundService` إدارة `WifiAwareManager.attach` و`WifiAwareSession`.
- أصبحت الخدمة تنشئ جلسة النشر باسم الخدمة `blousab-nearby` مع إعلان `BLUSAB2|userId|fingerprint` نفسه، وتنشئ جلسة الاشتراك.
- الخدمة تحتفظ بمراجع جلسات publish وsubscribe وتغلقها عند `stopWifiAware()` أو `onDestroy()`.
- `MainActivity.startWifiAware` يطلب من الخدمة بدء دورة الحياة، ويتلقى callbacks لاكتشاف المرشحين والرسائل وفقدانهم.
- عند الحاجة إلى الخدمة، يبدأ التطبيق الخدمة الأمامية ويربطها قبل طلب بدء Wi-Fi Aware.
- تم توجيه إيقاف Wi-Fi Aware إلى مالك الجلسات (الخدمة)، مع إبقاء تنظيف حالات البروتوكول وموارد NAN data path في Activity.
- تم تحديث إشعار الخدمة ليعكس وجود Bluetooth وWi-Fi Aware.

## ما بقي في Activity
هذه ليست عملية نقل كاملة لمحرك Wi-Fi Aware بعد:
- آلة المصافحة `BLUSAB_WIFI_HELLO / ID / PROOF` والتحقق من Ed25519 ما زالت في `MainActivity`.
- حالات `PeerHandle`، إدارة مفاتيح الجلسة، التحقق من البصمة، وقرار إظهار `wifiVerified` ما زالت في Activity.
- إنشاء NAN data path و`NetworkCallback` وSockets ونقل الحزم ما زال في Activity.
- callbacks المسجلة لدى الخدمة تلتقط Activity الحالية؛ لذلك لا نعدّ المصافحة أو إعادة إرفاق callbacks مستقلة عن Activity عند تدميرها. هذه حدود مقصودة موثقة، وليست ادعاءً بأن Wi-Fi Aware أصبح مستقلاً بالكامل.
- لا يتم فتح اتصال بيانات تلقائي لمجرد العثور على إعلان. يبقى طلب الاتصال الصريح والتحقق السابق شرطين كما في النسخة السابقة.

## الأمان والتوافق
- لم يتغير تنسيق الإعلان أو رسائل المصافحة، ولم يتم تخفيف التحقق من الهوية أو التوقيع.
- الإعلان يظل معرّفاً وبصمة مفتاح فقط، ولا يعرض اسم نظام التشغيل أو صورة/اسم غير موثق.
- الخدمة تملك موارد جلسة Aware وتغلقها عند الإيقاف. لا يعني ذلك استعادة جلسات NAN بعد قتل عملية Android؛ يجب إعادة attach وإعادة اكتشاف الأقران.

## الفحوصات
- فحوصات ساكنة: التحقق من استدعاء الخدمة لبدء Wi-Fi Aware، نقل `attach/publish/subscribe` إلى الخدمة، مسارات callbacks، وتوجيه stop إلى الخدمة.
- اختبار سلامة ZIP عبر `unzip -t`.
- لم يتم تنفيذ Gradle build أو Flutter analyze أو اختبار هاتفين؛ لم تتوفر بيئة Android/Flutter build متكاملة هنا. يجب بناء المشروع وتجربة هاتفين يدعمان Wi-Fi Aware قبل الاعتماد عليه.

## الخطوة التالية
المرحلة 28: نقل آلة المصافحة نفسها وحالة `PeerHandle` إلى الخدمة، مع واجهة أحداث محتفظ بها وإقرار استلام، ثم نقل إدارة NAN data path تدريجياً. يجب الحفاظ على signer callback الحالي وعدم إنشاء مفاتيح هوية جديدة.
