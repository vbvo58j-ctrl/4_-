# المرحلة 23 — تسليم أحداث جلسات Bluetooth مع إقرار الاستلام

## ما تغيّر
- أصبحت خدمة Android تحتفظ بأحداث جلسات Bluetooth في قائمة محدودة حتى تتلقى إقراراً من Flutter يحمل `eventId`.
- عند إعادة ربط مستهلك الأحداث، تعيد الخدمة إرسال الأحداث غير المؤكدة بدلاً من إزالتها بمجرد محاولة التسليم.
- أضيفت دالة `acknowledgeSessionEvent` ونداء MethodChannel باسم `ackSessionEvent`.
- أضيف `eventId` إلى `BlousabEvent`، مع منع معالجة الحدث نفسه مرتين داخل عمر Flutter engine، ثم إرسال الإقرار بعد تسليمه إلى بث الأحداث.
- الحد الأقصى لقائمة الخدمة 200 حدث؛ عند الامتلاء تزال أقدم الأحداث غير المؤكدة لتجنب نمو الذاكرة بلا حدود.

## حدود الضمان
- هذا تسليم at-least-once بين خدمة Android وFlutter أثناء إعادة ربط Activity/engine، وليس ضمان exactly-once على مستوى تخزين الرسائل.
- قائمة الأحداث في الذاكرة وليست دائمة عبر قتل عملية Android أو إعادة تشغيل الهاتف.
- رسائل المحادثة تظل محمية بمخزن outbox المشفر وإقرارات التسليم الموثقة؛ قائمة الأحداث ليست بديلاً عن ذلك المخزن.
- إذا انتهت عملية Flutter بعد إقرار الحدث وقبل أن تنهي طبقة التطبيق حفظ الرسالة، فالمعالجة النهائية تعتمد على إعادة مزامنة المحادثة/outbox.
- لم يتم نقل توقيع Ed25519 أو إنشاء جلسة المصافحة إلى Android Keystore؛ ما زال Flutter يوقع transcript قبل تسليم جلسة socket للخدمة.

## الفحوصات
- فحص ساكن لتطابق اسم النداء بين Kotlin وDart، وجود `eventId`، والاحتفاظ بالأحداث حتى الإقرار.
- لم يتم تنفيذ Gradle build أو `flutter analyze` أو اختبار هاتفين في هذه البيئة.
