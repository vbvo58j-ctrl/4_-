# المرحلة الثانية — شبكة Mesh (الخطوة 1)

## ما تم تعديله
- جعل حزم تأكيد التسليم (`delivery_ack`) وتأكيد القراءة (`read_ack`) قابلة للترحيل عبر الشبكة متعددة القفزات.
- إضافة معرّف مستقل لكل حزمة تأكيد، وحقول `recipientId` و`relayEnabled` و`hopCount` و`relayPath` و`createdAt` اللازمة لمرورها عبر عقد وسيطة.
- تحديث حزم الملفات لتحتوي على معرّف المستلم وحقول الترحيل نفسها الموجودة في حزم الرسائل، حتى لا تتوقف الملفات عند أول هاتف وسيط.
- بقيت حدود العمر وعدد القفزات ومنع تكرار المعرفات ومسار الأجهزة مطبقة في مسار استقبال الحزم.

## ما لم يكتمل بعد
- لا يوجد حتى الآن توجيه موجّه حسب هوية العقدة/المسار؛ الترحيل الحالي يعتمد على البث إلى الأقران المتاحين مع حدود القفزات ومنع التكرار.
- لا توجد خدمة مستقلة تعمل في الخلفية طوال الوقت؛ إعادة المحاولة مرتبطة بأحداث التطبيق/المحادثة.
- لا توجد مصادقة تشفيرية مستقلة لحزم الترحيل؛ يجب عدم اعتبار `senderId` وحده إثبات هوية.
- نقل الملفات عبر عدة قفزات ما زال يضع الحمولة كاملة داخل JSON/Base64، وهو غير مناسب للملفات الكبيرة ويحتاج تقسيمًا إلى أجزاء مع تحقق سلامة.
- ما زالت طبقة LAN مستخدمة في بعض المسارات؛ هذه الخطوة لا تدّعي استبدالها أو توفير Wi-Fi Direct.

## تحقق
- تمت مراجعة التغييرات نصيًا والتحقق من الحقول في حزم ACK والملفات.
- لم يتوفر Flutter/Dart في بيئة التنفيذ، لذلك لم يتم تشغيل `flutter test` أو `flutter analyze` أو بناء APK.
- يلزم اختبار فعلي بثلاثة هواتف: مرسل، وسيط، ومستقبل؛ مع اختبار رجوع تأكيد التسليم والقراءة عبر الوسيط.
